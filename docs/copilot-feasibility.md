# GitHub Copilot (Claude Opus 4.6) 辅助开发 AITTK 可行性评估

> **文档定位**：本文档评估在 VS Code 中仅使用 GitHub Copilot 扩展（模型：Claude Opus 4.6）作为主要 AI 开发助手，完成 AITTK 全域 AI 辅助决策系统（`docs_Plan_v7.1.md`）的可行性。所有推荐结论均为参考建议，最终工程决策权归开发者本人。

---

## 1. 总体可行性结论

**结论：可行，但需配合明确的工作流约束。**

Claude Opus 4.6 在代码推理、复杂架构理解和多文件上下文处理方面能力强劲，能够覆盖 AITTK 项目所需的绝大多数编码任务（C# Mod 开发、规则引擎设计、LLM 集成、UI Overlay）。
然而，受限于上下文窗口容量、工具调用链路、及游戏私有 API 的不透明性，部分关键决策仍需开发者主导。

## 3. 局限性与约束

### 3.1 上下文窗口限制

- Claude Opus 4.6 上下文窗口约 200K tokens，而 `docs_Plan_v7.1.md` 本身已约 60K+ 字符；叠加多个源文件后，单次对话可承载的完整项目上下文有限。
- **应对**：每次对话聚焦单一模块（如仅讨论 `CombatRecommender`），避免一次性粘贴整个 Plan 文档。

### 3.2 游戏私有 API 不可验证

- Copilot 无法运行游戏，无法验证反编译 API（如 `CombatManager.Instance`、`CardModel.DynamicVars`）在实际运行时的行为。
- 生成的调用代码可能存在版本差异、空引用或事件时序问题，**必须由开发者在游戏内实测**。

### 3.3 无法访问本地文件系统

- Copilot 无法直接读取 ILSpy 反编译产物（`.cs` 文件），需开发者手动粘贴相关片段作为上下文。

### 3.4 并发与性能热路径

- Plan 要求"热路径低分配、近零 GC"（§1.4），Copilot 生成的代码默认不保证此约束，需开发者逐段评审并使用 `Span<T>`、对象池等手动优化。

### 3.5 Mod 框架兼容性

- Copilot 对杀戮尖塔2 Mod SDK（BaseLib / BepInEx 等）的了解来自公开资料，不一定覆盖最新版本的 API 变更；Mod 加载机制、Harmony Patch 等需开发者验证。

## 4. 风险清单

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | Copilot 生成代码调用了已废弃或不存在的游戏 API | 中 | 高 | 每次生成后对照 ILSpy 反编译结果人工校对 |
| R2 | 上下文截断导致生成代码与已有模块接口不一致 | 中 | 中 | 对话前粘贴当前模块接口定义；使用 `#file` 引用源文件 |
| R3 | 规则引擎评分逻辑生成偏差（数学公式错误）| 低 | 高 | 编写单元测试 Golden Cases，人工审查权重参数 |
| R4 | LLM（Ollama）集成提示词生成质量不稳定 | 中 | 低 | 将提示词视为数据，单独维护并人工评审 |
| R5 | UI Overlay 与游戏渲染管线冲突 | 低 | 高 | UI 代码优先在 Copilot 中设计骨架，运行时由开发者在游戏内验证 |
| R6 | 过度依赖 Copilot 导致对代码缺乏理解 | 中 | 高 | 见 §6 工程师责任边界 |
| R7 | 生成代码引入 GC 压力（违反热路径约束）| 中 | 中 | Code Review 时明确检查 `new` 分配；使用 BenchmarkDotNet 验证 |

## 5. 推荐工作流

### 5.1 对话单元划分

将 Plan 的每个**工作项（Step）**映射为一个独立的 Copilot 对话单元，避免跨多个 Phase 混合讨论：

```
对话粒度示例：
  ✓ "帮我实现 Step 2.2 回合价值函数，接口见下方..."
  ✗ "帮我实现整个 Phase 2"
```

### 5.2 上下文注入策略

每次新对话开始时，注入以下内容（按优先级排序）：

1. 当前模块的接口定义（`.cs` 头部）
2. 依赖模块的接口摘要（仅签名，不含实现）
3. 相关的 Plan 章节（精简版，非完整文档）
4. 本次目标描述

### 5.3 代码审查检查清单

Copilot 生成代码后，开发者应逐项确认：

- [ ] 所有游戏 API 调用与 ILSpy 反编译结果一致
- [ ] 热路径函数无意外堆分配（检查 `new`、LINQ、装箱）
- [ ] 公共接口签名与 Plan §14 文件清单定义一致
- [ ] 单元测试覆盖 Golden Cases（§12.2）
- [ ] 异常路径有优雅降级（不抛出到游戏主循环）

### 5.4 VS Code 配置建议

```json
// .vscode/settings.json（建议项）
{
  "github.copilot.chat.localeOverride": "zh-CN",
  "editor.inlineSuggest.enabled": true,
  "github.copilot.enable": {
    "csharp": true
  }
}
```

- 使用 **Copilot Chat** (`Ctrl+Shift+I`) 进行架构级讨论
- 使用 **Inline Chat** (`Ctrl+I`) 在文件内快速生成/修改代码片段
- 使用 `@workspace` 指令让 Copilot 索引本地文件（需 VS Code Copilot 扩展 ≥ 1.200）

### 5.5 分阶段可行性评级

| Phase（来自 Plan v7.1）| 建议 Copilot 参与度 | 人工介入重点 |
|---|---|---|
| Phase 1: 数据层完善 | 高（80%+）| 验证 API 调用正确性 |
| Phase 2: 规则推荐核心 | 高（75%）| 评分公式、阈值参数 |
| Phase 3: UI Overlay | 中（60%）| 渲染 API 兼容性测试 |
| Phase 4: 非战斗域基线 | 高（80%）| 知识库内容准确性 |
| Phase 5: LLM 集成 | 高（85%）| 提示词质量、响应解析 |
| Phase 6: 选卡/事件/药水/遗物 | 高（75%）| 威胁驱动逻辑验证 |
| Phase 7: 扩展与打磨 | 中（65%）| 性能调优、用户体验 |

## 6. 工程师责任边界

> **核心原则**：Copilot 是高效的代码生成工具，不是工程决策者。

以下决策**必须**由开发者主导，Copilot 仅提供参考：

| 决策类型 | 原因 |
|---|---|
| 游戏 API 调用的正确性验证 | 只有在游戏内实测才能确认行为 |
| 评分权重与阈值的最终取值 | 依赖主观游戏体验，无法自动化验证 |
| 知识库（JSON）内容的准确性 | 游戏数值可能随版本变化，需对照游戏实测 |
| 性能热路径的最终优化 | 需 Profiler 数据，Copilot 无法访问运行时指标 |
| Mod 与游戏版本的兼容性 | 游戏更新可能导致 API 变更 |
| 安全性与稳定性的最终判断 | 不可让 AI 决定是否"足够安全"地发布 |

**Copilot 的合理使用边界**：
- ✅ 根据开发者提供的接口规格生成实现代码
- ✅ 辅助调试：分析错误信息、提供修复方向
- ✅ 生成测试骨架，由开发者补充实际断言
- ✅ 解读反编译代码、推断 API 语义
- ❌ 不应由 Copilot 决定架构取舍（如是否使用 Harmony Patch）
- ❌ 不应跳过人工测试直接发布 Copilot 生成的代码

---

## 7. 总结

在以下条件满足时，使用 VS Code + GitHub Copilot (Claude Opus 4.6) 完成 AITTK 项目是**完全可行**的：

1. **对话粒度控制在单一工作项级别**，避免上下文溢出。
2. **每次生成后人工校对游戏 API 调用**，以 ILSpy 反编译结果为准。
3. **规则引擎评分逻辑配套单元测试**，Golden Cases 覆盖关键场景。
4. **热路径代码由开发者主导审查**，Copilot 生成后必须 Profiler 验证。
5. **最终发布前由开发者完整通测**，Copilot 不替代游戏内集成测试。

在此工作流下，Copilot Claude Opus 4.6 可显著加速 AITTK 的实现进度，同时将工程质量和最终决策权保留在开发者手中。
